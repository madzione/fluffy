# fluffy: Go in Flutter apps

fluffy compiles a project's Go code into a C library called over `dart:ffi` (Linux, Windows, macOS, Android, iOS) or into WebAssembly (web), and generates a typed Dart API from the Go code. The Go signatures are the schema: there is no IDL and no hand-written glue. Underneath sits a small symmetric JSON message layer, so Go can also call Dart.

Your main jobs in a fluffy project are writing Go, running `fluffy generate`, and using the generated Dart. Most mistakes come from editing files fluffy owns, from code the generator can't see, or from forgetting that native platforms never run Go's `main`. The sections below explain each.

## Before you start

- `fluffy --version` checks that the CLI is installed. Install it with `go install github.com/madzione/fluffy@latest`. Its directory (usually `~/go/bin`) has to be on `PATH`, because the platform build hooks call `fluffy` during every Flutter build. A build that fails with a message about fluffy not being found means `PATH`, not code.
- Native targets need cgo: a C compiler on Linux, MinGW-w64 `gcc` on Windows, Xcode on macOS/iOS, the Android NDK for Android. Web needs nothing extra.
- When the project has a `.fvmrc`, fluffy runs `fvm flutter` for you. Run Flutter commands yourself with `fvm flutter ...` in such a project too.
- `fluffy help` prints the full usage if something here looks out of date.

## Project layout and who owns what

```
my_app/
├── golang/                  Go module "<package>/golang"
│   ├── go.mod               yours
│   ├── api.go               yours: //fluffy:export functions
│   ├── main.go              yours: fluffy.Start setup, main() calls fluffy.Serve()
│   ├── fluffy_api.go        GENERATED by fluffy generate
│   └── fluffy/              OWNED BY FLUFFY: the Go message layer
└── lib/golang/
    ├── golang.dart          yours: import this one
    ├── api.dart             yours: hand-written additions, must `export 'api.g.dart';`
    ├── api.g.dart           GENERATED by fluffy generate
    └── src/                 OWNED BY FLUFFY: the Dart message layer
```

- Never edit `golang/fluffy_api.go`, `lib/golang/api.g.dart`, `golang/fluffy/` or `lib/golang/src/`, and don't add files there. `fluffy generate` and `fluffy update` overwrite them and delete unknown files, so changes are lost. Change the Go code and regenerate instead.
- Commit the generated files, so Dart compiles right after a checkout (e.g. `flutter analyze` in CI).
- Go code can live anywhere: in `golang/`, in subpackages like `golang/todo/`, or in another module the `golang/go.mod` `require`s with a local `replace` (or via `go.work`). Packages from the module cache are only used for their types, so a dependency fetched from the internet can't contain `//fluffy:export` functions; bind its services from `golang/` instead.
- Import the Go API in Dart with `import 'package:<app>/golang/golang.dart' as golang;`.

## Commands

| Command | What it does |
|---|---|
| `fluffy create [--fvm <ver>] [--patch-gtk] [flutter create flags] <dir>` | `flutter create` + `init`, replaces the counter app with a Go demo. The directory must be the **last** argument. |
| `fluffy init [--patch-gtk]` | Adds fluffy to the existing Flutter project in the current dir: scaffolds `golang/` and `lib/golang/`, patches the build hooks, updates `.gitignore`, generates, `flutter pub add ffi`. Keeps existing user files and `lib/main.dart`. |
| `fluffy update [--patch-gtk]` | After upgrading fluffy: replaces the message layer, re-applies the build hooks, regenerates. Keeps user code. |
| `fluffy generate` | Writes `api.g.dart` and `fluffy_api.go` from the Go code. `--check` fails if they are stale (CI), `--watch` regenerates on every change. |
| `fluffy run [flutter run flags]` | Generate, build `web/golang.wasm` if the device may be a browser, `flutter run`. |
| `fluffy build <target> [flutter build flags]` | Generate, build the wasm for `web`, `flutter build <target>`. |
| `fluffy lib <linux\|windows\|macos\|android\|ios\|web>` | Builds **only** the Go library. Flags: `-o <dir>`, `--arch <list>`, `--sdk iphoneos\|iphonesimulator`, `--android-api <n>`, `--ndk-version <v>`, `--strip`. |
| `fluffy <anything else>` | Passed through to `flutter` without generating, e.g. `fluffy test`, `fluffy analyze`. |

`fluffy generate`, `update` and `run` work from any subdirectory of the project.

Native builds compile Go inside Flutter's build (CMake, Gradle and Xcode hooks), so plain `flutter run` works on native targets, but it does **not** regenerate the Dart API. Prefer `fluffy run`, or run `fluffy generate` after every Go change (or keep `fluffy generate --watch` running). The web target has no hook: use `fluffy run -d chrome` / `fluffy build web`, or `fluffy lib web` before a plain `flutter` command.

## The standard loop

1. Write or change Go code.
2. `fluffy generate`. Read its warnings: they point at code that silently didn't make it into the API.
3. Use the generated Dart (read `lib/golang/api.g.dart` to see exact names and types).
4. Check: `go vet ./...` and `go test ./...` in `golang/`, `flutter analyze` and `flutter test` in the app, `fluffy run -d <device>` for the real thing.

## Choosing how to expose Go

| Need | Use |
|---|---|
| A stateless function | `//fluffy:export` on a func |
| A service with state (DB, config, caches) that is set up once | `fluffy.Start` + `fluffy.Bind` |
| Go calling Dart (dialogs, platform APIs, progress) | an interface marked `//fluffy:dart` |
| Go pushing events nobody asked for, raw channels | `fluffy.Emit` / `On` / `Handle` / `Request` |
| A result that arrives over time | a function or method returning `<-chan T` → Dart `Stream<T>` |

### `//fluffy:export` functions

```go
// Add adds a and b.
//
//fluffy:export
func Add(a, b int64) int64 { return a + b }

//fluffy:export
func FindUser(ctx context.Context, id string) (*User, error) { ... }
```

```dart
final sum = await golang.add(2, 3);      // Future<int>
final user = await golang.findUser('42'); // Future<User?>, User is a generated class
```

- The directive must be in the doc comment directly attached to the func. A blank line between comment and `func` detaches it (the generator warns).
- Parameters: optional `context.Context` first, then any arguments. No variadic functions.
- Results: nothing, `R`, `error` or `(R, error)`. A Go error (or panic) fails the Dart future with `golang.GolangException` (`e.message`).
- Functions in `golang/` itself may be unexported and become top-level Dart functions (`Add` → `golang.add`). Functions in other packages must be exported and are reached through the package name: `todo.Version` → `golang.todo.version()`.
- Go doc comments become Dart doc comments.

### Services: `fluffy.Start` and `fluffy.Bind`

The service package stays plain Go (no fluffy import) and testable with `go test`. Wire it up in `golang/main.go`:

```go
func init() {
	fluffy.Start(func() error {
		db, err := openDB()
		if err != nil {
			return err
		}
		fluffy.Bind("todo", todo.NewService(db))
		return nil
	})
}
```

```dart
await golang.todo.add('Milk');
final items = await golang.todo.list(); // List<Item>
```

- **Native platforms load Go as a library and never run `main`.** Put setup in `fluffy.Start` (called from `init`), never in `main`; `main` only calls `fluffy.Serve()` for the web. `Start` runs once on Dart's first connect (not again on hot restart); requests wait for it, and if it returns an error every request fails with that error.
- `Bind` registers every exported method with a supported signature (same rules as functions) as channel `<ns>.<Method>`; others are skipped with a generator warning. `fluffy.Bind[todo.API]("todo", svc)` exposes only the methods of interface `todo.API`.
- In Dart each namespace is a class `Go<Ns>` reached through the constant `golang.<ns>`.

### Streams: `<-chan T` results

```go
//fluffy:export
func Clock(ctx context.Context) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		t := time.NewTicker(time.Second)
		defer t.Stop()
		for {
			select {
			case now := <-t.C:
				select {
				case out <- now.Format("15:04:05"):
				case <-ctx.Done():
					return
				}
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}
```

Go runs the function when Dart starts listening; cancelling the Dart subscription cancels `ctx`. Always close the channel, also on `ctx.Done()`. Streams have backpressure: Go stops receiving from the channel while 1024 values or 8 MiB haven't reached the Dart listener (e.g. a paused subscription), so a fast producer simply blocks on its send. The `ctx` of non-stream functions is never cancelled.

### Go calling Dart: `//fluffy:dart`

```go
//fluffy:dart
type UI interface {
	Confirm(ctx context.Context, question string) (bool, error) // request: waits for Dart
	Progress(percent float64)                                    // emit: fire and forget
}
```

The generator writes a constructor into `fluffy_api.go`: `newUI()` for an interface in `golang/`, `new<Pkg><Name>()` (e.g. `newTodoUI()`) for one in another package. Inject its result like any dependency: `fluffy.Bind("counter", &Counter{ui: newUI()})`. The interface can live in the service package, which then still doesn't import fluffy. Give request methods a `ctx`; without one they wait forever.

In Dart, implement the generated abstract class (named `UI`, or `TodoUI` for package `todo`) and register it early, e.g. in `main()`:

```dart
class AppUI implements golang.UI {
  @override
  Future<bool> confirm(String question) => showConfirmDialog(question);
  @override
  void progress(double percent) {}
}

golang.UI.register(AppUI());
```

### Raw channels

`fluffy.Handle[T, R](name, fn)`, `fluffy.On[T](name, fn)`, `fluffy.Emit(name, data)` and `fluffy.Request[R](ctx, name, data)` in Go; `golang.emitter.emit/request/subscribe` and `golang.receiver.on/handle/remove` in Dart. The generator types them only when the channel name is a **constant**; a dotted name like `"todo.progress"` goes into the `golang.todo` namespace. `Emit`s before Dart connects are queued (up to 1024); emits to a channel nobody listens to are dropped. A Dart handler that throws gives Go a `*fluffy.DartError`. Register handlers in `init` or `fluffy.Start`.

## Type mapping

| Go | Dart |
|---|---|
| `int*`, `uint*` | `int` (web: precision lost above 2^53) |
| `float*` | `double` |
| `string`, `bool` | `String`, `bool` |
| `[]byte` | `Uint8List` (raw bytes on the wire as an argument, result, stream value or a struct field of one; base64 deeper down) |
| `[]T`, `[N]T` | `List<T>` (nil arrives as empty list) |
| `map[string]T`, `map[int]T` | `Map<String,T>`, `Map<int,T>` (nil arrives as empty map) |
| `*T`, fields with `omitempty` (non-struct) or `omitzero` | `T?` |
| struct | generated class with `fromJson`/`toJson`, follows `json` tags like `encoding/json` |
| `time.Time` | `DateTime` (microseconds; zone becomes UTC) |
| `time.Duration` | `Duration` (microseconds) |
| type with `MarshalText` | `String` |
| `any`, interfaces, type with `MarshalJSON` | `Object?` |
| `<-chan T` result | `Stream<T>` |
| `error` result | throws `GolangException` |
| channels as data, funcs, complex | unsupported: `fluffy generate` fails |

Give `MarshalText`/`MarshalJSON` value receivers: with a pointer receiver `encoding/json` treats values and pointers differently and generation can fail. Same-named structs from two packages: the second Dart class gets a package-name prefix.

## Gotchas

- **The generator sees the web build.** It type-checks as `GOOS=js GOARCH=wasm`, so files excluded from js (`//go:build !js`, `_windows.go`, cgo-only code, …) are invisible to it, and it warns if they use the fluffy API. Keep every exported function, bound service and `//fluffy:dart` interface in files that build for js/wasm, and split only the platform-specific internals, e.g. `store.go` (`//go:build !js`, files on disk) next to `store_js.go` (localStorage via `syscall/js`) with the same functions. The Go code must compile for both native and `js/wasm`; check with `GOOS=js GOARCH=wasm go vet ./...` in `golang/`.
- **Long computations on the web freeze the app.** Go wasm runs on the browser's main thread and only yields when every goroutine is blocked. In a hot loop, call `fluffy.Yield()` periodically (about 0.05 ms on the web, a no-op natively) and stream partial results. Avoid `time.Sleep` for this: browsers stretch it to 4 ms or more per call.
- **Hot restart** reconnects Dart: Go cancels the old streams and fails its pending requests to the old isolate, but keeps its state and does not run `Start` again.
- **Generator errors** mean the runtime would misbehave: a channel registered twice, a channel used with different types, two things mapping to the same Dart name, unsupported types. Fix the Go code; don't work around it in generated files.
- If a native build fails because `fluffy_api.go` registers a function that was removed or renamed, the hook rewrites it and retries; still run `fluffy generate` for the Dart side.
- After upgrading fluffy, run `fluffy update` in each project. Hooks from older versions keep working but print a hint.
- Linux desktops other than GNOME show a thick GTK title bar; `fluffy update --patch-gtk` (or on `create`/`init`) fixes it.

## Testing

**Go:** functions and services are plain Go; test them with `go test ./...` in `golang/` (add `GOOS=js GOARCH=wasm go vet ./...` for the web build). The layer's own tests live in the fluffy repo, not in the project.

**Dart widget tests** run without the Go library through an in-memory fake Go side. Handlers are keyed by **channel name**: `<Func>` for functions in `golang/` (e.g. `'Add'`), `<pkg>.<Func>` elsewhere, `<ns>.<Method>` for `Bind`, `<Iface>.<Method>` / `<pkg>.<Iface>.<Method>` for `//fluffy:dart` interfaces. Exported functions and bound methods receive their arguments as a **list**; `Handle`/`On` channels receive a single value. Return JSON-shaped values (maps for structs, ISO strings for times).

```dart
final go = golang.Bridge.fake();
go.receiver.handle('todo.Add', (data) {
  final [title as String] = data as List<dynamic>;
  return {'id': 1, 'title': title, 'done': false, 'created': '2026-01-01T00:00:00Z'};
});
go.receiver.stream('todo.Watch', (_) => Stream.value([]));
// Fake Go calling a Dart //fluffy:dart implementation:
final ok = await go.emitter.request<bool>('todo.UI.Confirm', ['Delete?']);
```

**Integration tests** against the real library: `flutter test integration_test -d linux` (the hook builds Go). For the web, `fluffy lib web` first, then `flutter drive ... -d web-server`.

## Troubleshooting checklist

1. `fluffy --version` works and `which fluffy` is on the `PATH` the build sees (Xcode GUI builds add `~/go/bin`, `/usr/local/go/bin`, `/opt/homebrew/bin`, `/usr/local/bin`).
2. `fluffy generate` runs cleanly; read every warning.
3. `cd golang && go build ./... && GOOS=js GOARCH=wasm go vet ./...`.
4. `fluffy lib <target>` alone, to separate Go/cgo/NDK problems from Flutter ones. Android: set `ANDROID_NDK_HOME` or pass `--ndk-version`; Windows cross builds use `x86_64-w64-mingw32-gcc` unless `CC` is set.
5. A Dart call fails with `GolangException`: the message is the Go error or panic, or the channel has no handler (missing `Bind`, `Start` not run, generated file stale → `fluffy generate`).
6. Web blank page or loader error: rebuild with `fluffy lib web` / `fluffy run -d chrome`, check `web/golang.wasm` and `web/wasm_exec.js` exist and the `fluffy:begin` block is in `web/index.html` (`fluffy update` restores it).
